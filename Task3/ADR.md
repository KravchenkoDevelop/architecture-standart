### <a name="_qmphm5d6rvi3"></a>**Решение**

## Идея

Не допускать прямого доступа внешних или пользовательских систем к АБС.  
Между внешним контуром и АБС размещается специализированный сервис, который выполняет защитную и интеграционную роль:

- минимальное API для работы с клиентскими данными;
- минимальный UI поверх этого API (для операторов/сотрудников);
- обязательная аутентификация и авторизация;
- шифрование трафика (HTTPS/TLS);
- дополнительные механизмы защиты на уровне API.

---

## 1. Минимальное API

### Ограниченный контракт
- Только строго необходимые операции: получение агрегированной клиентской информации, списка продуктов, статусов заявок.  
- Отсутствие «универсальных» операций (например, `ExecuteSql`, прямые SQL-вставки, прокидывание сырых запросов в АБС).  
**Результат:** минимальная поверхность атаки и невозможность злоупотребления широкими универсальными методами.

### Чёткая модель данных
- API выдаёт DTO без чувствительных элементов: маскирование номеров счетов, только последние цифры карт, агрегированные суммы.  
- Внешнему контуру не раскрывается внутренняя структура АБС: таблицы, поля, технические коды ошибок.  
**Результат:** скрытие внутренней схемы снижает вероятность успешного взлома и реверса модели данных.

### Валидация входных данных
- Проверка всех параметров запроса: формат, длина, диапазон.  
- Только параметризованные запросы / ORM.  
**Результат:** защита от SQL-инъекций и некорректных данных даже при ошибках на уровне интеграции.

---

## 2. Аутентификация и авторизация

### Контроль доступа к API
- Допуск только доверенных фронтов: UI операторов, внутренние сервисы, системы с корпоративной аутентификацией (SSO, OAuth2/OIDC, Kerberos, JWT).  
- Каждый вызов API связан с конкретным пользователем или системой.

### Авторизация по ролям
- Права пользователя определяют доступные операции: чтение, корректировка, доступ только к выбранным продуктам или сегментам.  
- Ограничения по регионам, подразделениям, филиалам.

### Аудит действий
- Запись всех операций: кто, когда, по какому клиенту и какой объём данных запрашивал.  
**Результат:** соответствие требованиям ИБ и возможность расследования инцидентов.

---

## 3. Шифрование (HTTPS/TLS и прочие меры)

### Шифрование трафика
- HTTPS/TLS между UI → API → промежуточный слой → АБС (если поддерживается).  
- Использование современных криптосuites и запрет устаревших версий TLS.

### Шифрование данных при хранении
- Если сервис что-то кэширует или логирует — данные должны быть зашифрованы на уровне диска или СУБД (TDE, column-level encryption).  
- Управление ключами через выделенную инфраструктуру (KMS, HSM), а не хранение ключей в конфиге.

### Правила работы с логами
- Исключение из логов:
  - полных номеров счётов;
  - номеров карт без маскировки;
  - комбинаций ФИО + паспортных данных + дата рождения;
  - любых полных идентификаторов, по которым клиента можно однозначно восстановить.
- Использование токенов, псевдонимов, масок.



### <a name="_bjrr7veeh80c"></a>**Альтернативы**


### Идея

Прямой доступ к АБС даже через одно минимальное API остаётся рискованным.  
Рационально ввести **промежуточный слой**, который:

- экранирует АБС от внешних запросов;
- минимизирует объём чувствительных данных за пределами АБС;
- локализует последствия взлома, ограничивая ущерб только промежуточным уровнем.

---

## 1. Зачем нужен отдельный промежуточный слой

### 1.1. Изоляция АБС
- АБС располагается в глубоком, изолированном сетевом сегменте с отдельными ACL.  
- Промежуточный слой общается с АБС только по строго определённым интеграционным контрактам.  
- Внешние системы не могут обратиться к АБС напрямую — все запросы проходят через контролируемый шлюз.

### 1.2. Разделение ответственности
- АБС фокусируется на бухгалтерской корректности, балансах и транзакциях.  
- Промежуточный слой отвечает за предоставление безопасных агрегированных данных и API-интерфейсов.  
**Эффект:** защита и бизнес-логика развязаны, что облегчает развитие и снижает риски.

### 1.3. Снижение нагрузки на АБС
- Частые читающие операции (например: агрегаты, статусы, скоринговые данные) могут кэшироваться в промежуточном слое.  
- АБС не подвергается пиковым нагрузкам от фронтов или операторских UI.

---

## 2. Требования к защите от атак и шифрованию

### 2.1. Базовые векторы атак: SQL-инъекции, XXE, XSS
- На внешнем API: строгая валидация входа, параметризованные запросы, отсутствие прямого SQL.  
- На промежуточном слое: дополнительные фильтры — обращения к АБС реализуются только как фиксированные операции (`GetCustomerAggregate`, `GetProductsList`).

### 2.2. WAF, IDS и rate limiting
- Перед API: Web Application Firewall для отслеживания SQLi, path traversal, XSS.  
- Ограничение частоты запросов (rate limiting) предотвращает массовые переборы и скрейпинг.

### 2.3. Сетевые ограничения
- API и промежуточный слой находятся в отдельном, контролируемом сетевом сегменте (DMZ / приложений).  
- Доступ к АБС возможен только с хостов промежуточного слоя и только по строго разрешённым портам.

---

## 3. Политика по данным в промежуточном слое

### Основной принцип:  
**в БД промежуточного слоя не должно быть прямых идентификаторов клиента**.

### 3.1. Отсутствие чувствительных идентификаторов
- Не храним открытые `client_id`, `account_number`, `account_balance`, `last_change`.  
- Используем суррогатные ключи: токены, GUID, псевдонимы.  
- Маппинг хранится в АБС или в защищённом токенизационном сервисе.

### 3.2. Минимизация набора полей
Храним только данные, необходимые для быстрой аналитики:

- агрегированные статусы (наличие продукта, наличие задолженности, сегмент клиента);
- результат скоринга;
- параметры для подбора персональных предложений (лояльность, риск-профиль).  

**Всё детальное — только через таргетные запросы к АБС.**

### 3.3. Шифрование данных
- Даже «нечувствительные» данные шифруются на уровне диска или ячеек БД (TDE, column encryption).  
- Это усложняет повторное использование данных при компрометации.

### 3.4. Локализация ущерба
Если злоумышленник получил доступ к промежуточной БД:

- видны только обезличенные агрегаты и технические признаки;
- невозможно однозначно восстановить конкретного клиента, его счета и реальные балансы;
- АБС остаётся недоступной и несущественно затронутой.

---

## 4. Обоснование 


### 4.1. Безопасность
- Шифрование, сегментация, отсутствие прямых идентификаторов, строгое разграничение ролей → значительно уменьшают риск утечек ПДн и финансовых данных.  
- Промежуточный слой принимает основной удар при атаках и выполняет функцию «буфера безопасности».

### 4.2. Соответствие требованиям регуляторов и ИБ-политик
- Нет прямого доступа внешних систем к АБС.  
- Все вызовы проходят через аутентифицированный и логируемый API.  
- Применяются best practices из OWASP, Zero Trust и принципа минимальных привилегий.

### 4.3. Производительность и отказоустойчивость
- АБС перестаёт быть bottleneck’ом.  
- Промежуточный слой может горизонтально масштабироваться и кэшировать запросы.  
- При внешних атаках (например, DDoS) страдает внешний контур, но не АБС.

### 4.4. Эволюция архитектуры
- Промежуточный слой развивается независимо от АБС.  
- Можно добавлять новые API для мобильных приложений, внутренних сервисов, партнёров.  
- При обновлении АБС меняются только адаптеры интеграции, внешние контракты остаются неизменными.
