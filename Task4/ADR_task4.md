### <a name="_qmphm5d6rvi3"></a>**Базовое решение: интеграция с сайтом ЦБ + xlsx с макросом**


**Описание архитектурного решения**

**Компоненты:**

* Система колл-центра (CRM / операторское рабочее место).

* Внешний источник ставок — сайт/публичное API ЦБ.

* Общее файловое хранилище (сетевой ресурс, SharePoint, DFS и т.п.).

* xlsx-файл с макросом, который:

* при открытии обращается к сайту/API ЦБ;

* подтягивает текущие ставки;

* на основании формул рассчитывает ставку для клиента (тип продукта, срок, сумма, надбавки/скидки по заранее заданным правилам).

**Сценарий работы:**

* Оператор колл-центра в режиме консультации открывает xlsx с общего ресурса.

* Макрос автоматически запрашивает данные с сайта ЦБ.

* В xlsx по формулам рассчитывается ставка, которую оператор озвучивает клиенту или использует в скрипте.

* Для базового уровня консультации (узнать текущую ставку по типу продукта) оператору достаточно этого инструмента, даже без интеграции с АБС.

___

 **Сильные стороны решения**

Минимальное влияние на АБС.
Отсутствует прямое взаимодействие колл-центра с АБС. АБС не перегружается, не требуется доработка, нет рисков повредить критичный контур.

Своевременная и регуляторно корректная информация.
Используются данные ЦБ как официального источника базовых ставок/ключевой ставки. Это аргумент на стороне комплаенса и аудита: оператор опирается на публичный, проверяемый источник.

Быстрая реализация (time-to-market).
Для первоначального включения корректной информации в скрипты операторов не требуется строить новый бэкенд. 

Достаточно:

* настроить доступ к сайту ЦБ;
* разработать макрос и формулы;
* развернуть xlsx на расшаренном ресурсе.

Низкая стоимость владения на старте.
Нет нового сервиса, нет отдельного CI/CD, нет отдельного контура мониторинга. Основные затраты — поддержка xlsx и доступов к ресурсу.
___

**Ограничения:**
* Нет персонализации предложений.
* Макрос работает только от данных ЦБ и статических формул.
* Не учитывается:
    * история клиента;
    * его сегмент;
    * наличие других продуктов;
    *индивидуальные программы лояльности.

* Ограниченная управляемость и масштабируемость.
* xlsx сложно версионировать и централизованно обновлять без дисциплины и процессов;
* сложнее внедрять изменения тарифной модели «по кнопке».

___

**Риски:**
* риск, что у части сотрудников откроются старые копии файла;
* Риски с безопасностью и IT-управляемостью.
* макросы — зона повышенного внимания ИБ;
* xlsx плохо логируется как «источник истины» для принятых решений по ставкам;
* нет системных логов и метрик (кто, когда, какую ставку посчитал).
* Зависимость от доступности сайта ЦБ. (Если сайт/сервис ЦБ недоступен, макрос не сможет обновить данные).

### <a name="_bjrr7veeh80c"></a>**Альтернативное решение API колл-центров + промежуточное API между колл-центром и АБС**

**Целевая архитектура**

**Компоненты:**

* Call Center API — основное API для всех каналов колл-центра:

    * рабочие места операторов,

    * голосовые/чат-боты(при необходимости, внутренние порталы).

* Промежуточный слой (Pricing / Offers / Integration Service) между Call Center API и АБС:

    * поднимает отдельный микросервис/слой, отвечающий за расчёт ставок и получение предложений;

    * интегрируется:

        * с АБС (остатки, активные продукты, лимиты),

        * с источником ставок ЦБ (как с внешним справочником),

        * с внутренними справочниками и правилами скоринга/лояльности.

* АБС — источник клиентских данных и тарифных параметров, требующих высокой достоверности и транзакционности.

___
**Сильные стороны**

* Единая система получения информации по ставкам и предложениям для всех операторов и каналов. Вся логика расчёта ставок живёт в одном сервисе, а не размазана по xlsx, локальным скриптам и «памяти операторов».

* Поддержка индивидуальных условий.

* Возможность учесть сегмент, историю, программы лояльности;

* Возможность строить матрицы «для этого клиента сейчас выгоднее…»;

* Расширяемость под любые маркетинговые кампании.

* Безопасность и изоляция АБС.

* Колл-центр не ходит напрямую в АБС, а работает через интеграционный слой;

* Упрощённое управление доступами, логирование, аудит всех запросов к данным клиента.

* Индустриальный уровень управляемости.

* Версионирование правил и тарифных моделей (dev/test/prod);

* Логи, метрики, алерты;

* Нормальный CI/CD для изменений правил и интеграций.

* Переиспользуемость.

**То же API можно использовать для:**

* мобильного приложения,

* интернет-банка,

* внутренних порталов,

* автоматизированных ботов.

Снижает фрагментацию логики по каналам.

Готовность к регулированию и аудиту.

Все расчёты ставок могут логироваться с контекстом (исходные данные, применённые правила, результат);

Возможность объяснить, откуда взялась конкретная ставка для конкретного клиента.
___

**Проблемы альтернативного решения**

* Выше порог входа.

* Нужна полноценная реализация сервиса;

* Требуется интеграция с АБС, источником ЦБ, базами профилей/лояльности.

* Сложнее старт.

* Нужны инфраструктурные элементы (сервера, контейнеры, шины, API-шлюзы);

* Нужно время на постановку процессов разработки и поддержки.

* Это как раз логично позиционировать как целевое решение, к которому приходим после MVP.
